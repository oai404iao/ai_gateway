# 配置模型与路由

> 状态：当前。

客户端请求的是计价模型；网关把请求发给同一操作下的上游候选。管理员负责配置这些候选，API Key 决定调用者可以使用其中哪些渠道。

## 建立第一条路由

1. 在“上游凭证”创建通用静态凭证，并填写准确的允许 Base URL；无需认证的服务可在渠道中明确选择无凭证。Codex 改走[专用接入流程](codex.md)。
2. 在“上游接入”创建 `general` 接入，填写服务的 Base URL、代理和超时。Base URL 必须在凭证允许范围内。
3. 在“渠道配置”创建管理组和逻辑渠道，绑定接入与凭证。
4. 在渠道详情新增操作能力，例如 `chat_completion`，填入能力实际支持的 upstream model；模型发现只填充草稿，必须保存。
5. 在“模型配置”创建客户端计价模型，设置 USD 价格；为该模型添加同操作规则，选择能力、upstream model 和正权重，启用后保存。
6. 向 Gateway API Key 授予所属逻辑渠道的访问范围及 `proxy`；需要模型列表时还要有 `models.read`。普通用户自助 Key 必须受有效 Policy 允许。
7. 使用该 Key 按[快速开始](quickstart.md#5-发送第一个代理请求)发送请求。上游调用可能收费。

要修改转发的 Body 或 Header，打开「渠道配置 → 逻辑渠道详情 → 渠道接口能力」，选择目标操作，展开「请求体和标头转换」。可选择共用模板，再用可视化编辑器或 JSON 添加本能力的覆盖规则，最后保存接口能力。相同渠道下的其他操作不会被修改。

## 多个上游接入同一模型

如果渠道和操作能力已经建好，不需要为每个能力重复建立路由：

- **只登记上游模型**：在「渠道配置 → 全部渠道接口能力」或单个渠道的能力列表中勾选目标，点击「追加上游模型」。输入一个准确的上游 ID，或从所选的一个发现来源获取 ID。预览区分将追加和已存在的目录项；保存不覆盖其他模型，也不创建路由。
- **只给现有客户端模型加路由**：在「模型配置」选中模型，点击「批量配路由」。按接口操作核对不同接入、逻辑渠道的同名候选，可改选能力已登记的上游别名。选择目标优先级；同层已有的同一能力和上游 ID 不重复添加。此入口不改定价，也不登记模型。
- **一起上架**：在「模型配置 → 上架模型」输入客户端模型 ID。已有 ID 沿用本地计价；新 ID 可以手填价格、复制本地模型定价，或按准确 ID 查找并选择 models.dev 报价。进入候选预览后，只有确认上游支持该操作时才勾选未登记行的「登记并路由」。最后一次确认同时保存定价模型、所需的目录追加和路由候选。仅查找报价或预览不写入配置。

一次上架最多选择 100 个候选。新规则默认启用，新层采用加权随机，新候选权重为 1；原有规则的开关、层级策略、候选权重和 Key 授权不变。已有停用规则加入候选后仍需单独启用。若价格、所选能力或目标规则的版本已变，整次撤销，请重新加载预览再确认。模型发现和同名推荐不验证上游实际支持的操作，也不会自动绑定今后新增的渠道。

## 理解模型、能力和候选

`models.source_model_id` 是客户端模型身份，最多绑定一个 routing profile。每个 profile
按操作分别配置 `chat_completion`、`responses`、`responses-ws`、`web_search`、
`images_edit`、`images_generation` 规则；不会跨格式转换、降级或借用另一操作的路由。
停用规则可以是空草稿，启用规则必须包含非空 tier。

每个 tier 保存 `capability_id + upstream_model + weight` 显式候选。较低 priority
优先；在当前最低可用层内使用 `weighted_random` 或 `weighted_round_robin`。
同一能力可以使用不同 wire model 或出现在不同层；同层完全相同的能力/模型组合不能重复。
保存时 wire model 必须在能力目录中。计费始终使用 profile 的计价模型，转发使用候选模型。
后续移除目录模型、禁用组/接入/凭证/渠道/能力会影响可用性，但不会替换候选。

管理组组织渠道；接入指定连接器、地址、代理和超时。每个逻辑渠道选择一个组、一个接入及可选凭证。能力登记在渠道上，按操作设置模型目录、变换、压缩、倍率、探测和统计。所属渠道与操作创建后不可修改。

**授权跟随渠道，不跟随候选。** 直接授权逻辑渠道即覆盖其全部现有和后续能力。选组则覆盖该组当前成员，渠道移入即获授权，移出即失去该组带来的授权；单独授权该渠道的 Key 不受影响。普通用户只能在有效 Policy 的范围内选择。Policy 仅允许一个渠道时，不能据此选择整个组。

## 管理故障转移、自动禁用与定时测试

在 Console「系统设置」区分三个动作：

| 策略 | 何时使用 |
| --- | --- |
| 故障转移 `request_retry` | 普通请求尚未向客户端发送响应时，可尝试不同的能力/模型候选。默认最多重试 1 次，可设 1–10 次。默认不重试 HTTP 状态码；显式配置 4xx/5xx 可能导致上游重复执行和收费。[不重试的操作](data-plane.md#转发响应与重试)不受此设置影响。 |
| 自动禁用 `automatic_disable` | 同时开启系统开关和能力的 `auto_disable_allowed`。上游命中配置的 HTTP 状态码或错误关键字（不区分大小写）时，暂时排除该能力。 |
| 定时测试 `scheduled_testing` | `global` 测试配置了探测的合资格能力，`failure_only` 只测临时禁用的能力。默认每 5 分钟发送 `reply '1'`；可设置测试间隔、提示词，以及成功后是否自动恢复。 |

配置探测时，从能力目录选 `test_model`（发往上游的模型），再选 `test_pricing_model_id`（网关使用的计价模型）；两者可不同名。探测走实际接入的网络、变换与鉴权，发送非流式 Chat Completions 或 Responses 请求。图片、Codex、手工停用的渠道或组不参加。删除探测计价模型会清空这两个字段。

**定时测试会产生上游调用和费用。** 请求日志标记 `request_source = scheduled_test`，按价格快照、倍率和实际 usage 记入系统内部管理员及其 Key，不扣普通用户余额。自动禁用和恢复可在审计日志查到；手工恢复只清除临时禁用标记，不打开显式关闭的能力。

## Session 粘性

在系统设置的 `session_affinity` 中按顺序配置 Header 或 JSON Pointer（如 Responses 的 `/prompt_cache_key`、独立搜索的 `/id`）。第一条提取到非空标量的规则决定 Session Key。网关按规则、API Key 和模型规则隔离缓存，只保存会话值的哈希。

亲和记录指向上次完整成功的候选；只有它仍获授权、健康且处于最低可用优先级层时才优先使用。失败会清除映射，重试次数由故障转移设置决定。缓存有数量上限和 TTL，每个实例独立。管理员可在 Console 查看或清理，也可用 `GET/DELETE /console/v1/system/session-affinity/cache`；清理不改数据库规则。

## 保存与验证

控制面写入校验完整快照，提交后在当前进程发布；其他进程通过周期重载收敛。在途请求继续使用取得的旧快照。详情 `ETag` 必须用于更新；版本冲突时重新读取再编辑，不覆盖他人的修改。更多管理接口见[Console](console.md)，金额规则见[计费](billing.md)。
