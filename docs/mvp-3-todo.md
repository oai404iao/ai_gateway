# MVP 3 后端任务清单

目标：在已完成的 PostgreSQL 控制面、不可变运行时快照和单次代理转发之上，实现受限请求/响应变换与可复用的上游客户端管理。MVP 3 使管理员能够安全地配置模板、渠道覆盖和出口代理，同时保持流式响应、格式隔离和不重试约束。

## 范围与边界

- 本版本实现 `config_templates`、`channels.override_document`、`proxies` 与渠道超时字段当前已存在的数据库模型；它们由控制面编译进不可变快照，数据面不查询数据库。
- 只支持 OpenAI Chat Completions 与 Responses；两种格式的解析、变换验证和 SSE 事件处理路径必须分离，禁止在格式之间回退或转换。
- 变换固定顺序：模板默认值 -> 渠道覆盖 -> 上游认证。上游认证始终最后执行，变换不得改写认证或受保护/hop-by-hop 请求头。
- 透明路径优先：未启用任何 body 变换时保留原始请求 bytes；上游流响应默认逐块转发，禁止为普通代理响应整流缓冲。
- 仍然只允许单次上游尝试。响应头或任一响应字节发送后，不得重试、切换渠道或更换代理。
- 管理面普通读取和审计记录不得包含代理密码、上游密钥、Authorization/Cookie 等敏感字段；敏感字段只可通过明确、审计过的后续凭据操作处理。

## 执行约定

- 每个阶段开始前，将阶段目标和可验证子任务写入本文件；只有全部子任务、测试和提交完成后才开始下一阶段。
- 每完成一项就在本文件勾选；提交记录必须包含该阶段的实现、测试和清单更新。
- 阶段间保留既有测试，不以跳过或弱化既有行为换取进度。
- 配置写入必须通过现有 `ControlPlaneCoordinator`：同一事务内写入、读取完整候选控制面、编译、记录 allowlist 脱敏审计，然后提交并发布快照。

## 阶段 1：模板、代理与渠道策略快照

阶段目标：将模板、出口代理和渠道覆盖/超时从数据库完整编译为可安全发布的运行时快照，使现有渠道能够在不改变默认透明代理行为的前提下引用它们。

阶段状态：已完成

实现拆分：

- 控制面：补全代理和模板的事务读取、受控管理表示、乐观并发写入与脱敏审计。
- 编译快照：将代理、模板和渠道网络/变换策略编译为不可变强类型对象，并在发布前完成引用与安全校验。
- 管理 HTTP：提供代理与配置模板的列表、读取、创建、全量更新端点。
- 验证：用单元和隔离 PostgreSQL 集成测试覆盖失败回滚、脱敏与即时快照发布。

阶段设计记录：

- 变换文档采用封闭的 `version: 1` JSON DSL；非空文档必须指定匹配渠道的 `api_format`。编译结果为格式分离的不可变计划，模板层与渠道覆盖层按固定顺序组合。
- DSL 仅允许请求/响应头 `set`、`remove`、`rename` 及 JSON `add`、`replace`、`remove`；拒绝未知字段、脚本、表达式、重复/冲突目标和受保护头部。
- 代理仅接受 `http`、`https`、`socks4`、`socks5` URL；渠道只可引用启用的代理、模板。渠道显式超时必须为正数。
- 普通管理表示和审计绝不包含代理密码、模板文档或渠道覆盖文档；只记录 allowlist 元数据。

## 阶段 2：受限请求变换

阶段目标：在请求发送至上游前执行可预测、可验证的头部和 JSON 变换，同时保留无变换请求的原始 body bytes 与受保护头部。

阶段状态：已完成

实现拆分：

- 请求执行器：按模板、渠道覆盖、上游认证的顺序应用已编译计划，并在任一失败时停止于上游之前。
- Body 路径：无 JSON Patch 时保留原始 bytes；仅在已启用 Patch 时按格式解析、修改与重新序列化。
- 错误与安全：保护路由/认证头、维持格式隔离，将所有变换失败映射为安全的客户端错误。
- 验证：单元和代理集成测试覆盖顺序、字节保持、两种格式、失败零接触与现有流语义。

### 阶段 2 执行任务

- [x] 2.1 定义受限 DSL：请求头 `set`、`remove`、`rename` 及 JSON Pointer/Patch body 操作；所有操作使用显式 AST，不接受自由脚本或表达式执行。
- [x] 2.2 实现编译期文档结构、指针、Patch 类型和格式验证；禁改 `Host`、`Content-Length`、`Connection`、`Transfer-Encoding`、`Authorization`、`Proxy-Authorization` 及其他 hop-by-hop 头。
- [x] 2.3 在代理 use case 中按模板默认值、渠道覆盖、上游认证的固定顺序应用请求变换；模型 alias 仍遵循既有格式隔离规则。
- [x] 2.4 当未启用 JSON body 变换时直接转发原始 bytes；仅在启用 JSON 变换时解析并重新序列化 body，维持当前大小限制和错误映射。
- [x] 2.5 将无效 JSON、无法应用的受限 Patch 和受保护头部操作映射为安全的客户端/管理面错误，不接触上游且不泄露文档或凭据。
- [x] 2.6 添加单元与代理集成测试，覆盖顺序、头部保护、无变换字节保持、两种格式隔离、Patch 失败与上游零接触。
- [x] 2.7 运行格式化、静态检查和全部测试，并提交阶段 2。

## 阶段 3：响应与 SSE 事件变换

阶段目标：在不缓冲整个上游响应的前提下，支持受限响应头变换和逐 SSE 事件的 JSON 变换，并保留既有流空闲超时、取消和单次尝试语义。

阶段状态：已完成

实现拆分：

- 响应头：在首个响应头发送前完成清理与已编译的模板/渠道变换，之后不再发生路由重试或替换。
- SSE 流：实现跨 chunk 的增量帧解析与逐事件 Patch，只缓存当前未完成帧；未选择、非 JSON 和 `[DONE]` 事件逐字节传递。
- 终态：事件变换失败后立即终止流、保持既有取消传播和空闲超时；不创建后台 body 泵。
- 验证：覆盖跨 chunk、首事件低延迟、非 SSE 透明路径、事件失败、取消与空闲超时。

阶段设计记录：

- SSE 采用单一、拉取驱动的 body 状态机；不启动后台任务，只缓存当前未以空行结束的帧，并对帧大小设置上限。
- 仅变换与当前格式的已编译选择器匹配、JSON 对象合法的事件；`[DONE]`、未知/非 JSON 事件和 EOF 残留逐字节保留。模板与渠道同一选择器的 Patch 按既有顺序连续执行。
- 若一个匹配事件无法应用或序列化 Patch，立即丢弃上游并以安全 body 错误终止流，记录专属 `response_transform_failed` 终态；绝不伪造成功的 SSE 事件。
- 启用实际 SSE Patch 时上游请求强制 `Accept-Encoding: identity`；若上游仍以压缩 SSE 响应则在发送下游头前安全失败。被变换的响应移除 `Content-Length` 与校验/实体标签元数据。

### 阶段 3 执行任务

- [x] 3.1 定义独立于请求变换的响应头和 SSE `data:` JSON 变换计划；明确每个 API 格式允许的事件类型与不可变字段。
- [x] 3.2 在发送响应头前应用允许的响应头变换并清理 hop-by-hop 头；响应头发送后不得重试或切换渠道。
- [x] 3.3 实现增量 SSE 帧解析器：按事件边界处理 `data:` 载荷，支持跨 chunk 边界，未匹配或不含 JSON 的事件原样传递。
- [x] 3.4 对启用的 SSE JSON 事件执行已编译 Patch；单事件失败以协议安全方式终止流并记录终态，不缓冲后续事件或整条流。
- [x] 3.5 保持客户端取消向上游传播、流空闲超时和渠道/准入租约释放；变换层不得创建后台泵或吞掉 body 错误。
- [x] 3.6 添加跨 chunk、首事件低延迟、非 SSE 透明转发、事件 Patch 失败、取消和空闲超时集成测试。

## 阶段 4：上游客户端注册表与出口代理

阶段目标：按出口代理、TLS 与有效超时策略复用 reqwest 客户端，并将渠道级网络策略接入单次转发路径。

阶段状态：已完成

实现拆分：

- 策略：确定性合并全局 TOML 默认值与渠道连接/响应头/流空闲超时，并定义可哈希、无密钥泄露的客户端键。
- 注册表：进程级惰性客户端复用，支持 HTTP/HTTPS/SOCKS 代理和 `no_proxy_hosts` 的明确直连选择。
- 代理接入：选中渠道按有效策略获取客户端，维持单次尝试、被动健康、取消与流超时的现有行为。
- 错误与验证：代理不可用和各超时映射为安全错误；本地代理/直连、复用、快照替换和生命周期均有集成测试。

阶段设计记录：

- 注册表键由代理无凭据 URL、凭据域分隔指纹、排序后的 `no_proxy` 规则、连接超时和固定 `RustlsWebPkiRoots` TLS 策略构成；原始凭据不进入键、Debug、错误或追踪。
- 注册表进程级共享但有界 LRU 淘汰；客户端克隆保持进行中的响应，快照替换只影响后续请求的键解析，不原地替换客户端。
- 直接客户端显式禁用环境代理；配置代理使用 `Proxy::custom`，只在已编译规则匹配目标主机时直连，未知主机保持代理，绝不静默绕过。
- 客户端显式禁用 reqwest 重试，固定使用 rustls WebPKI 根；响应头与流空闲超时仍在请求生命周期外执行，只有连接超时参与客户端键。
- 渠道被动健康身份包含无凭据出站策略指纹；旧快照持有的租约继续只影响旧身份。每次成功发布快照后，注册表剔除不再被新快照引用的客户端键。
- 有效响应头超时必须严格大于有效连接超时；不满足时在接触上游前以安全配置错误拒绝。SOCKS4/4a 禁止凭据，SOCKS5/5h 要求成对且协议长度有效的凭据，并支持 `socks4a`/`socks5h` 远端 DNS。
