# 编写与维护文档

> 状态：当前。适用于项目 README、现行指南、参考和开发文档。

文档应帮助读者完成任务或理解一个边界，而不是要求读者先还原项目的实施历史。
组织依据见[Pi 文档研究](development/documentation-design.md)，全部入口见[文档索引](README.md)。

## 先确定页面职责

| 位置 | 回答的问题 | 不放什么 |
| --- | --- | --- |
| `README.md`、`README.zh-CN.md` | 是什么、支持什么、从哪里开始 | 全量配置表、完整 API 清单、实施进度 |
| `docs/README.md` 和分类索引 | 我现在应该读哪页 | 重复正文、发布状态堆叠 |
| `docs/user/` | 如何安装、调用、配置、运维和恢复 | 未实现计划、内部重构过程 |
| `docs/development/` | 如何修改、验证，以及为什么这样设计 | 未注明年代的旧验收结果 |
| `docs/reference/` | 外部协议是什么、网关兼容到哪里 | 完整复制第三方 API、把外部能力当作网关保证 |
| `docs/openapi/` | Console API 的机器可读定义 | 与生成类型平行的手工契约 |
| `docs/archive/` | 过去采用过什么方案 | 当前操作入口 |
| 子项目 README | 该组件如何构建、使用和验证 | 复制整个项目手册 |

保留 `user/development/reference` 的读者边界，在各层按任务导航。一个主题已有权威页面时
链接它，不为每次功能交付再建一个说明副本。`AGENTS.md` 是编码 Agent 的操作约束，
不是普通用户的安装入口；修改指令文件需单独审查其约束变化。

## 先让读者得到结果

开头用一段话说明本页解决什么问题、适用于谁。长文给出简短的页内导航；不要把
所有小标题复制成冗长目录。根据内容选择写法，不强制每页套同一组标题。

### 上手与操作指南

按执行顺序写前置条件、最小步骤、成功判据，再讲选项和排障。例如：

```markdown
# 启动某个组件

> 状态：当前。

本页说明……。已有环境请跳到……。

## 准备
## 启动并检查
## 配置选项
## 故障与恢复
## 下一步
```

命令附近说明工作目录、权限、占位符、预期结果及危险后果。新建、升级、恢复流程分开，
不要给已有部署提供会覆盖密钥或重建状态的“快速开始”。

### 概念、设计与契约解释

先定义实体和所有权，再写链路、顺序、不变量、失败行为和验证入口。
表格适合表达路径职责、状态转换、能力矩阵；代码块适合最小配置、调用和流程。
保留必要设计理由，但将旧阶段计划和历史验收明确隔离。

### 外部参考

区分以下三个层次：

1. 权威来源在所标版本或日期下描述的外部语义。
2. 网关实际兼容、拒绝或有意不实现的范围。
3. 由配置、插件或特定部署额外决定的行为。

保留精确来源和核对日期。只有真正重新检查来源才更新日期，改写措辞不算重新核对。
源码研究标出版本或 commit；不能用某个版本的观察断言上游最新状态。

## 状态与证据

在标题后尽早给出状态。现有检查要求用户/开发/归档页及指定根文件的前 12 行内有：

```markdown
> 状态：当前。
```

英文页面使用 `> Status: Current.`。根据实际情况选择：

| 状态 | 使用方式 |
| --- | --- |
| 当前 | 已实现、随代码持续维护的说明 |
| 部分实现 | 明确分别列出已实现和缺失范围 |
| 提案 | 不构成实现或部署承诺 |
| 已完成设计记录 | 保存决策背景，当前行为仍核对实现与契约 |
| 历史归档 | 仅供追溯，不用于指导当前部署 |

外部参考使用以下元数据；索引只需类型说明：

```markdown
> 类型：外部参考
> 最近核对：YYYY-MM-DD
> 权威来源：[官方文档](https://example.com/reference)
```

不要把“本轮通过”“已经全量验收”当作长期事实。测试命令是验证入口；历史结果需要日期、
环境、样本和适用限制，不能伪装为本次运行结果或生产容量承诺。

## 唯一来源与写作边界

| 内容 | 来源与同步要求 |
| --- | --- |
| Console API 形状 | `docs/openapi/console-v1.yaml`；生成前端类型，不手工维护第二份 |
| 公共 Header、顶层 body 与通用出站策略 | `docs/reference/request-allowlists.json`；Markdown 解释动作和维护流程 |
| 供应商策略与隐私 | 外部插件契约和实现；宿主文档解释边界，不复制提供商规则 |
| TOML 字段与默认值 | `src/runtime_config/mod.rs`，同步根配置和容器模板 |
| schema 与迁移 | PostgreSQL migrations 和 SQLite schema/生命周期实现 |
| 外部 API | 官方文档或固定版本源码；不以网关文档代替完整第三方参考 |

来源冲突时按[文档索引](README.md#来源优先级)核查，不凭某页写了“当前”就覆盖代码或契约。
修正文档不得暗中改变接口、安全、计费或恢复语义。

保留各文档现有语言；中英文 README 的关键功能、入口和限制保持一致。
直接描述动作和限制，避免宣传性保证、空泛目标和重复进度说明。

## 文件、链接与示例

- 文件名使用小写 kebab-case，一个文件一个主要主题，一个 H1，标题不跳级。
- 命令、字段、路径、类型与端点使用反引号；代码块注明语言。
- 仓库内使用相对链接，链接文字说明目标任务，尽量直达相关小节。
- 改名、移动或重命名标题前全仓搜索引用，包括代码注释、脚本、CI、技能和发行打包。
  旧入口仍有用途时保留明确的导航锚点，不留两个正文副本。
- 凭据只用不可用的占位符。不要复制真实 API Key、JWT 私钥、登录状态、数据库密码或生产请求。
- 安全建议说明它防住什么、没有防住什么；原生插件启用不是沙箱，软额度不是硬费用预留。

## 变更同步矩阵

| 变更 | 同时检查 |
| --- | --- |
| 公共 API 或请求策略 | 请求策略 JSON/解释、用户操作指南、兼容性参考、README 和相关测试 |
| Console API | OpenAPI、生成声明、前后端调用点、spec 集成测试 |
| 进程配置 | 两份 TOML 模板、用户配置文档、配置测试和相关 Agent 约束 |
| schema、结算、备份恢复 | migration、开发契约、用户恢复说明、双后端测试 |
| 转发、Streaming、插件 | 兼容性边界、插件职责、确定性测试和真实上游验证说明 |
| Console UI | 子项目 README、架构/交互指南、组件/浏览器验证 |
| 发行与部署 | 部署、发布指南、README、产物打包与许可证材料 |
| 文档路径或标题 | 分类索引、全仓旧路径/锚点、脚本、源码链接和发行包内容 |

## 验证并报告

在任务 worktree 根目录运行：

```bash
git diff --check
python3 scripts/check-docs.py
```

脚本检查覆盖范围内的本地 Markdown 链接文件、单一 H1 与状态/参考元数据。
它不验证页内锚点、命令是否可运行、外部链接有效性或事实准确性；这些需要按变更核对。
子项目文档也应检查链接和入口，不因不在脚本枚举中而免于验证。

脚本或源码注释同时修改时补充对应语法/格式检查。文档改写本身不要求运行付费上游、
负载测试或启动生产服务；报告只列实际执行的检查与未验证的边界。
