# 测试设计与审查

> 状态：当前。适用于网关、Console、系统验收和交付工具的测试。

先说明**什么回归必须被发现、谁能观察到它**，再选输入和断言。审查时问两件事：如果实现正确、只是换了写法，这个测试还会通过吗？如果行为真的坏了，它会失败吗？运行命令和环境要求见[选择验证层级](getting-started.md#选择验证层级)。

## 让实际结果与预期相互独立

- 从契约取得预期：例如 [Console OpenAPI](../openapi/console-v1.yaml) 定义响应形状；计费例子可以手算预期余额。不要用被测的计费、掩码或序列化函数同时生成期望值。断言夹具里预先写好的值，只能说明夹具是什么，不能证明网关发送、拒绝或保存了什么。
- 选择能区分成功与失败的数据。分页上限为 100，就准备超过 100 行；要证明拒绝一个旧字段，就从已知能提交的请求出发，只改变该字段。对于鉴权、扣费、重试和持久化，检查对应错误码及副作用，而不只是“非 200”或“返回数组”。
- 在承诺发生的边界观察。凭证轮换要在模拟上游收到的请求上验证；“不派发”要计入上游收到但未通过校验的请求；“恢复不重扣”要在重启并完成结算后核对账本。使用合成哨兵检查秘密不外泄，断言失败也不能把秘密作为实际值或预期值打印出来。
- 对被测操作，mock 只接受预期的方法、目标和请求形状。未知调用不应获得通用成功响应；后台请求出错即使没显示在页面上，也应能让对应测试失败。测试“已保存”时，保存前后的数据必须可区分。

## 按契约选比较方式

| 要证明的事 | 合适的检查 | 容易误判的替代品 |
| --- | --- | --- |
| 公开错误码、协议标记、未变换的字节透传 | 在真实输出上精确比较错误字段、帧或字节 | 只在整个响应里搜索某个词 |
| JSON、TOML、工作流或数据库的语义 | 解析字段与类型；没有顺序约定时比较集合；数据库约束用元数据和会触发约束的写入验证 | 搜注释、缩进、SQL 片段或序列化后的空格 |
| Console 的可见行为 | 操作有可访问名称的控件，检查选中项、可见值或实际请求；布局在浏览器检查溢出或尺寸 | 以 CSS 类名、DOM 包装层或复制整份词典证明交互或显示正确 |
| 架构、ABI、构建和发行不变量 | 检查依赖边界、类型、协议描述符、构建元数据或最终制品 | 以源码出现某个拼写证明运行时行为 |

精确值本身不是问题：若顺序、文案、调用次数或字节就是兼容要求，应把它固定下来。反之，即使检查的是用户可见的输出，也不要固定契约未规定的格式。例如 SSE 事件顺序有意义，但一个事件不一定对应一个 HTTP chunk。结构检查可以单独守住架构边界；只有规则本身就是文本规范时，才用文本检查直接证明它。

## 给 Agent 和维护者的验收依据

评估编码 Agent 的补丁时，验收条件应允许不同的正确实现。评估多轮工具调用时，区分任务结果与路径：若测的是工具结果能否被网关带回下一轮，就核对实际返回的哨兵和关联 ID；若测的是一般任务能否完成，则某一串工具名不能代替结果。不要仅为让错误实现通过而改断言、改夹具或跳过失败项。

清理测试时，对每个拟删断言指出**哪一条保留测试、在哪一层、仍能发现同一回归**。组件有点击测试不代表服务端已实施授权；PostgreSQL 与 SQLite 各自的约束、协议旧代际兼容，也不能只因输入相似就合并掉。必要时用一个合法对照和一个只改动目标条件的反例核查判据，不以用例条数衡量覆盖。

以上取舍参考 [Google：只检测实现变动的测试](https://testing.googleblog.com/2015/01/testing-on-toilet-change-detector-tests.html)、[Anthropic：按任务结果设计 Agent 评测](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) 和 [OpenAI：用结构测试执行架构约束](https://openai.com/index/harness-engineering/)。这些是设计依据，不是网关的外部协议。
