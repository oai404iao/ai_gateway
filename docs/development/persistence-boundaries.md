# 持久化边界与独立计量事实

> 状态：当前设计记录。基于 `9c020c0`（第一阶段 PR #176）设计；P1–P3 已实现，P4 提供小数据量成对备份恢复演练，不等于生产容量认证。
> 本阶段范围已确认包含独立计量事实，不能以仓储拆文件代替结算与查询投影解耦。

P1 的现有行为与可执行测试见[持久化行为契约基线](persistence-contracts.md)，
P2 的接口见[持久化操作接口](persistence-interfaces.md)，P3 的实际 schema/流程见
[独立计量事实](independent-metering.md)。本文保留原设计与分阶段验收，第二节记录重构前起点。

## 1. 目标与范围

本阶段把“业务必须保证什么”与“PostgreSQL 怎样实现”分开：

1. 应用层不再接触 `PgPool`、`Transaction<Postgres>`、`sqlx::Error` 或 SQLSTATE。
2. 控制面存储、计量事实与结算、请求日志查询具有独立接口和职责。
3. 金额精度、原子性、幂等、重放和约束成为可执行契约。
4. 保留 PG 的 COPY、UNNEST、行锁、advisory lock 和索引优化，但不暴露给业务调用者。
5. 结算和拼车恢复不再等待 Console 查询日志投影成功。

不在本阶段实现 SQLite、替换 SQLx、引入 ORM/Kafka、改变收费策略、自动补账或日志删除功能。
不扩大第一阶段准入范围，不更改本地 spool/slot 和拼车 WAL 的耐久保证。
PR #176 的非阻塞 Rust 缓存整理告警独立处理，不混入本设计。

接口可替换不等于 SQLite 已可用；未来后端还必须实现同一约束、迁移与并发契约。

## 2. 已核实的起点

当前行为仍以[数据库架构](database-architecture.md)、
[日志耐久化](request-log-durability.md)和代码为准。

| 当前位置 | 耦合与必须保留的行为 |
| --- | --- |
| `src/application/control_plane.rs` 的 `mutate`、`compile_transaction` | 应用编排 PG 事务；变更、完整快照编译校验、审计在提交前完成；提交后发布。进程内串行门覆盖写入与重载。 |
| `src/application/codex/mod.rs` 的 `refresh_credential_locked`、`reset_quota` | 应用持有 PG 事务/行锁期间访问外部服务；generation 校验、失败状态提交和兑换串行化不可顺带改变。 |
| `src/application/system_metrics.rs`、`src/http/console.rs` | 上层读取 PG pool 状态，HTTP 还解释 SQLSTATE/constraint 名；错误翻译未收拢。 |
| `src/persistence/mod.rs` 的 `RequestLogRepository` | 一个仓储兼任 ingress、宽表写入、查询、统计和余额结算。 |
| 同文件的 `settle_batch` | `request_logs.billed_at` 是唯一认领标记；与余额扣减、Key 额度增加在一个事务提交。 |
| `src/persistence/codex_sharing.rs` 的 `sharing_completed_costs` | 拼车 WAL 恢复读取 `request_logs.cost_amount`；与普通账户结算不是同一笔状态更新。 |
| `src/persistence/codex.rs` | Codex 窗口费用也聚合查询日志；必须纳入费用读路径迁移。 |
| `src/workers/durable_request_log.rs` | COPY 提交后推进 spool checkpoint；宽表持久化成功后删除 ingress；坏行保留并延迟重试。 |
| `src/workers/mod.rs` 的 `RequestLogWorker` | 内存队列旧入口仍被测试使用；不能只改生产 worker、让测试继续验证旧结算链路。 |

第一阶段已实现派发前同步 intent/slot。只有 intent、没有可信终态时保留待核对，
不伪造失败、不自动记零，也不因此冻结普通用户。intent 本身不能证明已派发。
这一选择继续有效；拼车对活跃窗口的 uncertain 限制仍按其独立 WAL 契约执行。

重构前成功缺 usage 的日志费用为 NULL，自动结算与 settlement backlog 都不包含它；
无费用的 rejected、账户归属异常也不能等同于“可重试待扣款”。
新边界必须显式区分这些情况，不能用一个 `pending` 或 `COALESCE(cost, 0)` 掩盖差异。

## 3. 目标职责与接口

以下为拟议名称，不是已经存在的源文件或 API。先按实际用例建立小接口，不建设通用 CRUD、
通用事务执行器或“一切都实现 Repository”的框架。

| 边界 | 对外能力 | 不应拥有 |
| --- | --- | --- |
| `ControlPlaneStore` | 一致性读取、经过校验的配置变更、审计和乐观并发；返回完整候选记录 | 快照发布、HTTP 状态码 |
| `IdentityStore` / `ConnectorStateStore` | 身份会话、OAuth/配额状态的原有专用操作 | 任意 SQL/连接访问 |
| `TerminalEventStore` | 耐久接收事件批次、完成计量物化、获取/完成日志投影工作、重试状态 | 账户扣费、Console 筛选 |
| `MeteringStore` | 不可变计量事实、确定费用批量读取、费用统计、未知/异常分类 | 查询日志的生命周期 |
| `SettlementStore` | 原子结算、未结算扫描、结算结果/回执读取 | 公共 `claim` 后由调用方自行扣款 |
| `RequestLogQueries` | 受权限约束的日志列表/详情及非财务查询 | 结算、COPY、物理删除计量事实 |

同一 PG 连接池可支撑多个接口；职责拆分不等于每个接口新建连接池。
保留当前控制面池与日志流水线池的隔离及资源上限。

拟议代码组织以 `src/persistence/` 为公开契约入口，PG 实现逐步归入其 `pg` 子模块；
领域计量类型放在 `src/domain/`。只移动实际跨边界使用的 DTO，避免一次搬迁全部类型。
PG 行映射、`FromRow`、`QueryBuilder` 和错误 source 留在实现内。
组合根 `main.rs`、migration 实现及 PG 集成测试允许使用 SQLx。

### 3.1 控制面：保留校验事务，隐藏底层事务

最终使用操作专属的 prepared-change 对象，而不是把 PG 事务换名为公共 `DbTransaction`：

```text
coordinator 持有现有 serial 门
  -> store.prepare_change(actor, command, expected_version)
       在内部事务中验证身份/版本并执行变更，读取完整候选记录
  -> application 编译候选并校验上游策略
  -> prepared_change.commit(audit)
       同事务写审计并提交；失败/取消/丢弃对象则回滚
  -> application 发布已验证的完整快照
```

prepared-change 只提供本操作的候选读取、提交和放弃能力，不提供 executor、
任意表修改、通用 `begin` 或内部事务访问器。迁移全部控制面入口，包括批量更新、
自助 Key、自动禁用/恢复和手工 reload，不能只覆盖管理员单条 mutation。
校验失败不得出现持久化修改、审计成功记录或新快照。

数据库事务和 ArcSwap 不构成一个原子事务：提交后进程退出时，启动/重载从已提交数据恢复。
保留现有发布顺序与串行门，不在本阶段新增分布式发布协议，也不宣称多个运行时订阅者原子更新。

Codex refresh/reset 使用各自的操作 guard：只暴露锁定的凭证状态及完成/失败提交方法。
外部 HTTP 仍由应用发起，暂时保留原有锁覆盖范围和 generation 判断。
不把网络调用移进 PG 仓储，也不自动重试可能已经轮换 token 或消费兑换额度的操作。
缩短这些长事务需要单独设计 lease/fencing 与提供方不确定结果处理，不作为接口重构附带工作。

### 3.2 错误与观测

PG 内部把 SQLSTATE、约束名、行数异常翻译成稳定的语义：
`Conflict`、`NotFound`、具体业务约束、`Unavailable`、`InvalidFact`、
`ReplayConflict`、`CommitOutcomeUnknown` 等。底层错误供内部诊断，不作为 HTTP 分支条件。
不把所有 unique/FK 错误都粗暴翻译为同一个 409。

Console 保留现有错误码、权限、ETag/If-Match 和响应形状。池状态由存储健康快照返回，
应用层不持有 `PgPool`。不要在本轮增加查询页面或自动核对 API。

“临时错误”不是无条件可重试：提交结果未知时，计量写入和结算按 UUID 重新查询/重放；
无幂等键的控制面创建、外部 OAuth/兑换不能盲重试。

## 4. 独立计量事实模型

采用两个事实实体，物理名以实施时 migration 为准：

| 拟议实体 | 内容与所有权 |
| --- | --- |
| `request_metering_facts` | 每个可信终态 UUID 一行；请求/账户身份、开始/完成时间、来源、协议/操作、最终渠道与定价身份、usage、有效价格快照、费用及费用分类；写入后不可变。 |
| `request_settlements` | 每个已结算 UUID 一行；引用计量事实，记录结算金额、时间和规则版本；主键同时是唯一结算认领键。与余额/额度更新一起提交。 |

**两者都不得外键依赖 `request_logs`。** 回执只引用计量事实。
保留对用户/Key 等历史身份的约束和墓碑可追溯性，不要求相关实体仍处于 active 状态；
软删除不能让已发生的费用消失。

事实保留费用归属和统计需要的维度；不复制 prompt、响应正文、Header、密钥或错误详情。
实施前逐项列出既有费用查询的维度，避免拆表后通过 JOIN 查询日志才能完成金额统计。
可保留查询日志内的旧价格/费用字段作为不可变展示副本，但它们不再拥有结算权。

### 4.1 费用状态与处理状态分开

| 费用分类 | 判断来源 | 自动结算 |
| --- | --- | --- |
| 已知费用 | 当前终态包含可信费用，可能本来就是 0 | 是 |
| 策略归零 | 明确 `failed` / `cancelled`，按既有业务规则取 0，usage 可缺失 | 是，写一次零额回执 |
| 待核对 | 成功但费用未知，或计量证据不足 | 否，不能伪造 usage 或金额 |
| 不适用 | 无费用的 rejected，或当前不可计价的 standalone web search | 否；不是欠费也不是零额已结算 |
| 证据异常 | 有费用但缺少合法结算所需的模型/价格事实等 | 否；保留异常，不因费用非 NULL 自动扣款 |

判断以实际终态为准；不能把“所有 cost=NULL”归为免费，也不能新增
`request_source=scheduled_test` 的免单规则。定时探测的系统身份、定价与结算保持现状。
现有不提供可计价 usage 的操作也不得借拆分改变计费方式或拼车可用性。

另行区分“可结算但未处理”“已经结算”“账户归属异常”“事件冲突”等处理结果。
不使用持久化的半完成 `settling` 状态；事务失败后仍是未结算。

只有 intent 的请求不是可信终态，继续留在第一阶段本地待核对证据中；
不为了填满新表制造一条费用为零的事实。对账可见性应区分本地 intent 未决、
数据库未知费用、账户异常与正常 settlement backlog。
本阶段只补充内部计数/诊断与核对查询，不扩展 Console 公共响应。

新表不能丢失 migration `0061` 的 `request_logs_billed_state_check`：
旧日志可以合法保存尚不具备结算条件的记录，“费用非 NULL”本来就不是充分条件。
下列约束必须移到 PG 计量/回执实现，同时有领域验证和直接 SQL 约束测试：

| 类别 | 允许回执的必要条件 | 约束归属 |
| --- | --- | --- |
| 已知费用 | 费用非负；`model_id`、currency、token 计价单位、生效时间和四项有效单价完整；沿用现有范围约束 | 事实分类与字段约束；回执插入再次验证资格 |
| 策略归零 | outcome 明确为 failed/cancelled 且费用为 0；不强制价格/usage 存在 | 事实 CHECK；回执资格 |
| 待核对、不适用、证据异常 | 不允许回执 | 回执写入的数据库级保护，不能只靠 worker 查询过滤 |
| 所有允许结算的事实 | Key 属于原 user；回执 UUID、金额与事实一致，存在价格时币种一致 | 原子结算条件与 PG 跨表约束/触发器；更新集合校验 |

事实与回执均不可任意更新/删除。回执约束不能通过 JOIN `request_logs` 实现。
历史未 billed 且价格不完整的行保留为异常，不能在回填时“补当前价格”或升级成可结算。
历史已 billed 却不满足原有约束的行必须令迁移失败；两种情况不能混为一谈。

### 4.2 金额共同契约

- 保留 `Decimal` 和 PG 现有精度：有效单价 12 位小数，费用/余额/Key 已用额度 8 位小数，
  普通金额列 `numeric(24,8)`；拼车配置的 `numeric(20,8)` 不顺带扩大。
- `Cargo.lock` 当前锁定 `rust_decimal 1.42.1`；本地依赖源码的 `round_dp` 使用
  `MidpointNearestEven`。将现有行为固定为显式策略及 golden tests，不改成另一种舍入。
- 先按现有倍率路径得到 12 位有效价格，再按 token 单位计算最终 8 位费用；
  不改成分项先取整，不改成长整型最小单位或浮点数。
- 拼车每席位预算继续使用 8 位 `ToZero`，不能与普通价格舍入合并。
- 重放和历史迁移复制当时的有效快照与费用，不按当前模型价格重新计算。
- 费用非负；缺费用不等于 0。余额和 Key 额度保留软配额、可透支语义。
  单条/批量聚合溢出或存储精度越界必须整笔拒绝/回滚，不截断、不饱和。

### 4.3 唯一结算事务

```text
读取符合完整结算资格且账户归属正确的事实
  -> INSERT 唯一回执，只有本事务新插入的 UUID 获得结算权
  -> 按用户扣减余额，按 Key 增加已用额度
  -> 校验更新集合/金额与认领集合一致
  -> COMMIT
  -> 发布进程内 soft-quota 更新
```

回执先插入不等于先提交。任何一步失败，回执、余额和额度一起回滚。
相同 UUID 的并发/重复请求只可能产生一次账户变更。
多账户批次采用稳定锁顺序，序列化/死锁失败重试整个事务；不得重放单个扣款语句。
提交成功但回复丢失时，重试读取已有回执；不能再扣一次。
进程内额度通知丢失不影响数据库结算事实，沿现有快照重载机制恢复。

P3 实现另有 PG 内部 `request_settlement_pending` 工作集合，避免每轮扫描全部已结算历史：
首次物化事实时原子创建，结算时原子删除；重放不再创建已完成工作。

这是“至少一次投递 + 幂等账户效果”，不是端到端 exactly-once 或上游调用恰好一次。

拼车 WAL 仍单独计席位/用户窗口用量，不改成数据库余额账本。
其恢复从 `MeteringStore` 读取确定费用，不要求账户回执已经出现，
也不新增第二条余额扣减路径；相同 UUID 的 `finish` 仍按既有 WAL 幂等。

## 5. 流水线：先物化事实，再独立投影

```text
现有 intent/slot -> 终态 journal/spool
  -> TerminalEventStore.accept_batch
       PG 内部 COPY 到现有 durable ingress
  -> 计量物化阶段
       解码/规范化 -> 写计量事实 + 标记可投影（同一 PG 事务）
       ├─ SettlementStore 扫描事实 -> 回执 + 余额/额度
       ├─ MeteringStore -> 拼车恢复、费用统计、Codex 窗口费用
       └─ 日志投影阶段 -> request_logs -> 成功后删除 ingress
```

推荐复用 `request_log_ingest` 并增加计量阶段标记、分阶段重试信息及相应索引；
暂不新增消息系统或第二份整包 outbox。具体 PG 列和批次 SQL 属实现细节。
物化事务必须把“事实已持久化”与 ingress 可投影状态一起提交。
日志读取只领取已完成计量阶段的条目；未通过物化的行不可被日志 ack 删除。

应用 worker 只接触事件批次、稳定工作标识及语义结果，不知道 COPY 文本编码、
PG identity sequence、UNNEST、表名或 advisory lock。
PG 的工作标识可包装为不透明类型，不能要求未来后端模拟 PG 序列。

### 5.1 提交、重放与冲突规则

| 中断位置 | 恢复规则 |
| --- | --- |
| slot 完整、尚未进入数据库 | 沿第一阶段恢复相同 UUID；缺可信终态继续待核对。 |
| 数据库耐久接收后、spool checkpoint 前 | 重放 ingress；接收确认必须代表整个批次已提交，部分成功不能确认整批。 |
| 计量事务提交前 | 事实与阶段标记均回滚；原 ingress 仍在。 |
| 计量事务提交后、日志投影前 | 结算可继续；日志留待重试，不重新计算或扣款。 |
| 日志 INSERT 后、ingress 删除前 | 日志幂等重放；删除必须晚于投影持久化。 |
| 回执/账户更新后、客户端获知结果前 | 以回执判定是否已经结算，不能凭超时判断未提交。 |

同 UUID 的计量重放必须比较规范化后的身份、usage、价格、费用及必要归属维度；
不能仅 `ON CONFLICT DO NOTHING` 就称为幂等。同内容确认成功，不同内容保留并告警，
不覆盖已接受事实、不重新扣款，也不自动用后来内容冲正。
旧 journal 缺省字段和失败/取消归零必须先按既有兼容规则规范化，再比较。

计量等价不代表日志完全等价：同 UUID 的非财务字段冲突由日志投影处理并保留证据，
不得覆盖先前日志。费用冲突与日志冲突使用不同诊断，已有有效结算不因展示字段冲突撤销。

坏行必须隔离退避，不阻塞后续正常事实。JSON/journal 不能解码或财务事实无效时不能计量；
只与日志有关的约束失败（如展示状态字段非法）不应阻塞已验证的计量。
日志投影不能锁住 fact/settlement 表来“同步”状态。

### 5.2 查询、统计与保留边界

- Console 日志的 `billed_at` 从回执 LEFT JOIN 得到，保持响应与过滤语义；
  不由结算事务回写日志，否则宽表故障仍会阻塞扣款。
- 普通成本统计、排行榜、Codex 窗口费用和拼车恢复改读计量事实。
  保留原时间边界、request source、权限、group/channel 维度和过滤条件，
  不能擅自把“有成本”改成“已结算”口径。
- 排行榜物化快照可继续存在，但来源变为计量事实；
  成本事实早于日志展示可见是明确的最终一致性行为，需要文档与测试覆盖。
- 对每个旧查询列出旧源、新源、权限、NULL、时间和聚合精度对照表后再切换；
  禁止财务决策暗中回退读取日志副本。
- 本阶段不启用日志删除/TTL。未来删除查询投影不得级联删除事实/回执。
  事实和唯一回执保留必须覆盖可能重放的全部 UUID；不具备重放水位/幂等墓碑设计前不得清理。
  只留事实而删回执会重新开放结算权，同样禁止。
- 长期日志故障仍会累积 ingress 并消耗同一 PG 的空间和 I/O；本设计解除的是逻辑依赖，
  不是资源故障隔离。积压监控保留，不宣称日志故障可无限期无成本运行。

## 6. 迁移与发布：单一结算权硬切换

不支持新旧结算者滚动混跑，也不采用两张表分别认领的“临时双写”方案。
边界重构可以先合并；新增 schema、历史回填、生产写路径切换及所有财务读取切换必须作为
同一可发布切片验收。实施编号为 `0063_independent_metering_facts.sql`。

### 6.1 发布前预检

在隔离数据库上用历史 schema/数据样本演练：

- 统计总行数、已结算数量、金额分组总和、缺 usage、零费用、墓碑、账户异常及 ingress 积压。
- 验证所有旧 `billed_at IS NOT NULL` 均能形成同 UUID/费用/时间的回执；
  异常组合必须使迁移失败并给出有界诊断，不能静默跳过。
- 测量回填事务时长、锁等待、WAL 与额外磁盘占用，形成停机容量要求。
  此为实施验收，不等于已获准运行 forwarding 性能压测。
- 一致性备份业务数据库与所有实例 spool；启用拼车时包含其完整 WAL/检查点。

### 6.2 停机与原子迁移

1. 停止旧版本接流量，排空在途并停止所有旧 worker/实例。保存未知 intent；
   不要求丢弃或伪造结清未知证据。允许保留待恢复的 spool/ingress。
2. 在既有 migration advisory lock 和事务批框架下新建计量事实/回执及 ingress 阶段状态。
3. 从历史 `request_logs` 复制计量事实；已 billed 行复制回执，不更新余额或额度。
   未 billed 且满足完整结算资格的历史行留给新结算者，缺费用/缺价格按分类保留。
4. 校验 UUID 覆盖、费用及时间逐项一致、分类计数和分组金额总和；
   不是仅比较总金额。回填中任何失败回滚整个批次。
5. 移除日志表的结算认领权：删除物理 `billed_at`，
   调整原“仅允许一次 billed_at 更新”的触发器/约束为日志不可变保护。
   Console 查询使用回执别名返回原 `billed_at` 字段。
   旧结算 SQL 必须失败，不能继续成为第二个合法写入口。
6. 同步部署所有新版本实例，恢复原 spool；已回填 UUID 的再次重放走事实等价检查。
   检查新回执、账户增量、日志查询、拼车恢复和队列进度后恢复流量。

不改已部署 migration，不新增 `-- no-transaction` 或新的枚举提交屏障。
现有 `0034` / `0046` 历史屏障继续保留。

### 6.3 回退

迁移未提交时可回到旧版本；提交后不能直接回滚二进制，因为结算权已改变。
优先 forward-fix。必须整体恢复时，停止所有写入并恢复同一时点数据库和全部 spool/WAL，
并核对停机点之后的上游使用证据；不能只还原数据库造成重放/金额窗口倒退。
若历史规模使单事务停机回填不可接受，应暂停发布并另行设计在线迁移，
不能临时拆事务或放宽唯一结算保证。

## 7. 实施顺序与验收

| 切片 | 内容 | 退出条件 |
| --- | --- | --- |
| P1：固定行为契约 | [契约基线](persistence-contracts.md)：金额 golden tests、现有状态分类、PG 原子/幂等/约束测试与费用读写路径 | 基线测试覆盖普通、失败/取消、未知、rejected、探测、拼车；无生产语义变更 |
| P2：收拢接口 | 控制面/Codex 专属操作边界、错误翻译、pool 健康接口、分离仓储职责 | application/http 无 PG 类型与 SQLSTATE；既有 API/快照行为不变 |
| P3：独立事实切换 | [已实现的独立事实](independent-metering.md)：0063、回填、计量、回执、读源迁移 | 日志投影停滞不影响计量和结算；旧结算入口被移除；迁移故障可原子回滚 |
| P4：系统故障验收与运维 | 系统 E2E/PG 故障契约和[成对备份恢复演练](persistence-rehearsal.md)；旧认领/迁移入口拒绝 | 完整验收门禁通过，停机与恢复操作可复现；容量结论限于验收的数据与环境 |

P3 与 P4 均通过前不得发布独立事实版本。P3 内部可分有序提交，但不能把尚有双认领、
未回填或仍依赖日志恢复的中间状态作为可发布结果。

### 7.1 必须新增或强化的测试

| 测试 | 验收事实 |
| --- | --- |
| 中点舍入、最大金额、批量累加溢出、价格变更后重放 | 金额逐位一致；越界不产生半笔回执/余额 |
| 同 UUID 顺序/并发/提交回复丢失重放 | 一份事实、一份回执、一次余额与 Key 增量 |
| 同 UUID 不同费用/身份；仅日志字段不同 | 分别命中财务/日志冲突；不覆盖、不二次扣款 |
| 回执插入后、用户更新后、Key 更新后注入失败 | 三类状态全有或全无 |
| 直接锁住或拒绝写 `request_logs` | 计量、余额/额度和拼车恢复仍推进，日志 backlog 可观测且随后可恢复 |
| 成功缺 usage、失败缺 usage、只有 intent | 分别待核对、零额回执、只保留本地证据；普通用户未知不新增冻结 |
| 路由前拒绝、定时探测、不可计价操作 | 不改变当前收费/准入范围，不把 NULL 变成零额已结算 |
| 软删除用户/Key/渠道/模型后结算与重放 | 历史身份可追溯，费用不丢失，权限不扩大 |
| 有费用但缺模型/价格的未 billed 历史行；直接 SQL 伪造回执 | 前者保留异常不扣款；后者被新边界约束拒绝，零费用失败例外仍有效 |
| PG 接收/checkpoint、计量标记、投影 ack 边界崩溃 | 原始证据可恢复，无提前确认/删除、无双扣 |
| 拼车成功/失败/未知、重启、跨窗口 | 按既有 WAL 规则释放/保留预占；无第二次余额扣款 |
| 旧日志+已 billed+旧 journal+重复 ingress 升级 | 回填不改余额，首次恢复仅扣未结算费用，逐 UUID 对齐 |
| 回填中断/约束失败、旧 worker 写入 | 原子回滚；切换后旧 billed_at 写路径失败 |
| 并发控制面修改、编译失败、审计失败、提交后退出 | 版本冲突正确；无部分配置；启动恢复已提交完整快照 |
| Codex refresh/reset 并发、失败和取消 | 保留锁/generation/失败提交行为，不自动重复外部操作 |
| Console 列表、billed 过滤、统计、排行榜 | 形状/权限/金额口径不变，允许且验证事实早于日志可见 |

行为契约测试通过领域端口调用；PG 专属锁、COPY 和迁移故障另有集成测试。
不以 Mock 仓储通过代替真实 PG 并发与约束验证，也不预先创建空的 SQLite 实现。

实施门禁为项目 Rust format/clippy/workspace tests、相关 Console spec、系统 E2E 和文档检查；
需要时同步 OpenAPI/generated types 及前端门禁。替换内存旧 worker 的测试入口或让它复用同一
计量/结算接口，禁止保留第二套结算实现。
触及 forwarding/Codex 请求路径的切片还需经授权的 real-upstream smoke；
历史会话的付费测试授权不自动扩大到本次实施。本次设计工作不运行付费调用或压测。

## 8. 完成定义

完成不是“文件更小”，而是同时满足：

- 应用/HTTP 不知道 PG 事务和错误方言，控制面原子性与发布时序不变。
- 唯一费用来源为独立计量事实，唯一普通账户认领来源为结算回执。
- 日志投影故障的确定性测试证明结算和拼车恢复不依赖查询表。
- 历史回填、旧事件恢复、金额规则和约束均由契约测试固定。
- 本地未决证据、未知费用和异常归属不被静默当作零费用成功。
- COPY 等优化仍在 PG 内部；没有以抽象化为由削弱数据库约束或耐久性。
