# 模型上架：从能力目录到操作路由

> 状态：已完成设计记录。线框中的渠道、模型和价格为合成示例；末节是验收条件，不是运行结果。

管理员要让两家上游同时承接一个客户端模型，不应在四个能力编辑器与两个操作规则之间反复抄模型名。这里把三个动词分开：**登记**是把上游模型 ID 追加到能力目录；**配路由**是把指定能力和上游模型加入某个操作的某一层；**上架**是一次确认模型价格、必要登记和路由。登记本身不是路由，配置完成也不是授权或连通性测试。

## 从哪一步开始

| 我现在要做什么 | 入口与范围 | 确认前应看见什么 |
| --- | --- | --- |
| 只补能力目录 | 跨渠道从「渠道配置 → 全部渠道接口能力」进入，也可从单个渠道进入。勾选 1–100 项，点「追加上游模型」，与「批量编辑接口能力」分开。手输一个 ID，或从一个已选能力获取模型后选一个。 | 模型 ID、选中能力数；逐项列出逻辑渠道、操作和「将追加／已存在」。只对有增量的预览开放确认，不覆盖原目录，也不改路由。 |
| 给已有客户端模型快速配路由 | 在「模型配置」选中模型，点操作区的「批量配路由」，直接进入候选步骤。原来的逐条编辑器仍用于配置自定义权重、调整或移除既有候选。 | 已有价格只读；按操作列出同名匹配、可手选的已登记别名，以及目标层中已配置的候选。缺少登记时不能借这个入口修改能力目录。 |
| 第一次上架，或把缺少的登记和路由一起补齐 | 「模型配置」页头的「上架模型」打开独立页面。第 1 步确认身份与价格，第 2 步选择候选并核对变更，只在最后提交。 | 已有客户端 ID 则「沿用现有价格」。新 ID 须明确手填、复制某个本地模型价格，或选择 models.dev 中完整 ID 匹配的目录报价。目录查找不是导入，同名多报价时显示来源让人选择，不用第一个结果代选。 |

## 桌面：按操作比较，而不是按供应商配置两遍

下面是第 2 步的**信息顺序**。假设上游接入「北辰」与「南岭」各有一个逻辑渠道，同时提供 Chat Completions 和 Responses。三个能力已登记 `demo-chat-v2`，仅「南岭 B / Responses」尚未登记；管理员明确同意在该行登记后纳入路由。

```text
返回模型配置
上架模型                    2 / 2　选择候选并核对
demo-chat-v2                新建 · 手动价格　[返回修改]

操作 / 目标层                  上游接入 / 逻辑渠道     上游模型 ID         所选动作
Chat Completions · 优先级 0    北辰 / A                demo-chat-v2       ☑ 加入路由
                              南岭 / B                demo-chat-v2       ☑ 加入路由
Responses · 优先级 0           北辰 / A                demo-chat-v2       ☑ 加入路由
                              南岭 / B                demo-chat-v2       ☑ 登记并加入路由

核对本次变更
新建客户端模型 demo-chat-v2 · 手填价格（USD / 1M Token）
输入 0.80　缓存命中 0.08　缓存写入 0.90　输出 2.40
追加目录：南岭 / B / Responses → demo-chat-v2
新建并启用 2 条操作规则；每条在优先级 0 加 2 个候选，权重各 1
                                                    [确认上架]
```

- **对照价格，不混用名称。** 客户端模型 ID 与发往上游的模型 ID 分开标注。第 1 步及最终核对都能确认价格来源、单位与实际金额。已有模型不显示覆盖价格的控件；目录查不到不等于价格为零，允许改为手填或复制。
- **对照候选，不误认支持。** 分组标题是操作，行中同时出现接入和逻辑渠道。同名指完整 ID 相等，不用显示名、子串或大小写近似替配。可用且已登记同名、尚未配置的候选可以预勾选为草稿；管理员能取消，停用规则不预勾选。上游发现只提供线索；没登记的行默认不写，可手选已登记的别名，或在联合上架中明确选「登记并加入路由」。别名和追加登记均不自动勾选。
- **对照变更，不重建规则。** 选择目标优先级时可见已有层和策略；新增层为加权随机，新增候选权重为 1。若目标层已有同一能力和同一上游 ID，显示「此层已配置（权重 7）」之类的实际值，不把它计入新增。同一组合在别层不等于此层已有。已有停用规则要写「仍停用」，不能呈现成「即将启用」。

## 手机：同样的差异，一次读完一个对象

```text
返回模型配置
上架模型 · 2 / 2
demo-chat-v2
新建 · 手动价格

Responses
北辰 / A
上游模型　demo-chat-v2
☑ 加入路由（权重 1）
目标优先级　[ 0 ▾ ]
─────────────────
南岭 / B
上游模型　demo-chat-v2　未登记
☑ 登记并加入路由（权重 1）
目标优先级　[ 0 ▾ ]
             ⋮
核对本次变更
模型 1　追加目录 1　操作 2　新增候选 4
…价格、具体能力和层级明细…
[返回修改]　[确认上架]
```

手机不把选项和确认做成左右两栏：在每个操作下按「渠道 → 上游模型 → 动作与目标层」纵排，长 ID 可换行。能力追加弹窗也让每个目标与其状态相邻，短横屏可滚到最后一行和取消／确认；不靠悬停读取原值，也不用横向拖动填写同一行。沿用 [Console 视觉规范](../../design.md) 的 Nova 控件、语义颜色与可见焦点；不改变[模型工作区原有的宽窄屏切换](console-ux-review.md)。

## 状态、焦点与恢复

| 时点 | 显示与操作 |
| --- | --- |
| 还没选／没有匹配 | 提示「选择要加入的能力」；无完全同名时引导选择已登记的别名，缺少操作能力时指回渠道配置。不要把加载中或读取失败写成“没有能力”。全都在目标层时提示「所选候选已配置，无需新增」。 |
| 核对 | 确认动作旁展示本次增量，而不是整个系统的记录总数。选择别的模型、报价、能力或层后，旧核对结果不能继续提交；返回修改保留当前草稿。步骤切换让键盘焦点到新步骤标题；复选框的可访问名含操作与渠道，状态有文字而非只靠颜色。 |
| 提交中／失败 | 提交中禁用重复确认。字段无效时提示在相应输入旁，焦点可达首个错误。版本冲突提示「配置已变更，请重新读取并核对」，整批不部分成功，不自动重试；追加弹窗刷新预览时保留所填 ID，目标已删除则要求重新选。网络中断结果未明时提示先重读结果，不断言“未保存”。 |
| 成功／退出 | 能力追加只报告实际更新数；模型上架后能打开目标客户端模型核对操作规则。不声称“所有 Key 现在可用”。关闭弹窗返回触发处，退出独立页面返回模型工作区；已有草稿沿用[离开确认](console-interaction-standard.md#草稿与保存)。 |

## 实现验收

真实 Chromium 候选核对截图：[桌面 1440×900](model-onboarding-ux/review-desktop.webp)、[手机 390×844](model-onboarding-ux/review-mobile.webp)。两张截图均使用线框中的合成数据。

以桌面 1440×900、手机 390×844 验证上图同一份样本，另用 320px 宽、短横屏和键盘检查长名称与操作可达性。[上架浏览器用例](../../web/console/e2e/model-onboarding.spec.ts)通过 `pnpm --dir web/console e2e e2e/model-onboarding.spec.ts --trace on` 运行；mock 请求可以验证选择范围，不能证明实际数据库的提交边界。

1. **只登记**：对一条已登记、一条缺少该名的能力追加同一 ID。核对前无写入，确认后仅后一条新增；原目录中其他名字、模型价格、候选与授权不变。
2. **只配路由**：目标层已有一个权重 7 的候选，启用状态和选路策略均有历史配置。只勾选另一条已登记的能力。核对只多一个权重 1 的候选，原权重、层、策略与开关不变；未登记的能力没有被顺手补齐。
3. **联合上架**：按线框操作，确认应为 1 个新计价模型、1 项目录追加、2 条新规则、4 个候选。取消「南岭 / B / Responses」后应立即变为 0 项追加、3 个候选，不因它与另一个渠道同名而重新选中。确认为空、冲突或取消预览时均不能提交未核对的变更。
4. **错误可恢复**：核对后从另一会话修改一条目标规则，原草稿提交收到冲突。未看到假成功；重读后能看出差异，管理员重新核对前无第二次写入。手机和键盘可从第一项走到确认、返回修改和错误提示，页面本身不横向溢出。

实际模型、授权与路由边界见[配置模型与路由](../user/routing.md)，写入形状见 [Console OpenAPI](../openapi/console-v1.yaml)。
