# 派发前预留终态，计量独立于日志查询

> 状态：已采纳。

**问题。** 上游可能已收费，即使客户端断连或本地磁盘随后写满。只在完成时写日志无法撤回调用。把查询日志行同时用作账单，又使投影故障、删除或清理日志与扣款权耦合。

**选择。** 选路后先同步 intent，预留可写的终态槽。终态进入数据库后物化不可变事实；查询日志和结算独立消费。账户增量只来自本事务新插入的唯一回执。PostgreSQL 用 COPY、SQLite 用事务 INSERT 接收，二者的 checkpoint 都只确认已提交的批次。

**为什么不用更简单的方案。** 内存队列不能跨进程崩溃保留证据；事后写失败再告警也不能保护已经派发的调用。[Monoize 的请求日志实现](https://github.com/Ikaleio/monoize/blob/7b5624a36d6bd23162241443e9c1dae89eddebce/src/handlers/request_logging.rs) 提供了派发前准入的参照，而不是对本项目持久化或性能的证明。保留日志上的已扣费标志仍依赖查询行存在；独立回执可在日志不可见、重复交付时判定该 UUID 是否已经扣款。

**代价。** 准入增加本地同步与容量开销，计量与投影可以短暂不同步。intent 只证明做过预留，不证明已派发或已取得 usage。缺可信终态时保留证据待核对，不自动重试、记零或冻结整个用户；因此仍有未决费用风险。恢复与容量边界见[日志耐久化](../development/request-log-durability.md)，资格与幂等细节见[计量事实](../development/independent-metering.md)。
