# MVP 2 后端任务清单

> 历史归档：本文件记录 MVP 2 完成时的范围；其中“当前”“暂不纳入”等描述不代表当前实现。请以 [`mvp-usage.md`](mvp-usage.md) 和 [`mvp-4-todo.md`](mvp-4-todo.md) 为当前运行状态来源。

目标：将当前基于 TOML 的最小数据面接入 PostgreSQL 控制面，提供可热更新的配置、可持久化的请求日志，以及安全的多渠道选路能力。

## 执行约定

- 每个阶段开始前，将阶段目标和可验证的子任务写入本文件；只有全部子任务、测试和提交完成后才开始下一阶段。
- 每完成一项就在本文件勾选；提交记录必须包含该阶段的实现、测试和清单更新。
- 阶段间保留已通过的测试，不以跳过或弱化既有行为换取进度。

阶段目标：以 PostgreSQL 的一致性读取结果编译完整、不可变的数据面快照；重载失败不影响正在使用或后续获取的旧快照。

- [x] 1.1 为控制面读取定义强类型记录、仓储和迁移启动入口。
- [x] 1.2 在可重复读只读事务中读取 API Key、模型规则、渠道组和渠道，并映射数据库枚举与数组字段。
- [x] 1.3 编译和校验跨表引用、格式、启用状态、认证字段和重复路由；失败信息不暴露密钥。
- [x] 1.4 将启动、手动重载和定时重载接入 `RuntimeConfig`，仅在新快照完整编译成功时原子替换。
- [x] 1.5 将静态 TOML 路由记录移出生产配置路径，并更新示例配置和启动说明。
- [x] 1.6 添加 PostgreSQL 集成测试，覆盖迁移、编译校验、原子替换、重载失败回退和在途快照隔离。
- [x] 1.7 运行格式化、静态检查和全部测试，并提交阶段 1。

- [x] 在同一一致性快照中加载相关配置，并校验 Key、规则、组和渠道的格式/启用状态/引用关系。

- [x] 添加 PostgreSQL 集成测试：迁移、编译校验、原子替换及在途请求保持旧快照。

## 阶段 2：持久化请求日志

阶段目标：在不阻塞请求或缓冲流响应的前提下，为每个已选路请求异步、幂等地写入一条终态 `request_logs` 记录。

### 阶段 2 执行任务

- [x] 2.1 定义带稳定 UUID、选路上下文、状态码、TTFT、总耗时和错误分类的请求结果事件，并映射到 `request_logs`。
- [x] 2.2 实现有界非阻塞队列、单独写入 worker 和幂等插入；队列饱和或写入失败只产生可观测事件，不阻塞或破坏代理响应。
- [x] 2.3 将成功、上游失败、响应头超时、流空闲超时和客户端取消连接到一次性终态事件。
- [x] 2.4 明确未选路策略：无效认证、权限拒绝和无法解析模型仅写结构化追踪事件；已认证的未知或无权访问模型写入 `rejected` 请求日志。
- [x] 2.5 添加隔离 PostgreSQL 与代理集成测试，覆盖各终态、队列饱和、写入失败、取消和重复事件幂等性。
- [x] 2.6 运行格式化、静态检查和全部测试，并提交阶段 2。

- [x] 定义与 `request_logs` 对应的请求结果事件，包含渠道、规则、格式、状态、TTFT、总延迟和结果。
- [x] 建立有界异步日志队列与写入 worker，避免请求链路逐条同步写数据库。
- [x] 为成功、上游失败、响应头超时、流空闲超时和客户端取消写入一次日志。
- [x] 明确并实现认证失败、未知模型等未选路请求的日志策略。
- [x] 添加队列饱和、worker 写入失败、取消及幂等写入测试。

## 阶段 3：多渠道选择与被动健康检查

阶段目标：从不可变快照中的多渠道候选按最低优先级和渠道权重选择一次，并在快照外维护可并发访问的被动健康状态。

### 阶段 3 执行任务

- [x] 3.1 将规则编译从“唯一候选”扩展为去重的渠道组与直接渠道候选，并校验最低优先级组的选择策略一致性。
- [x] 3.2 实现最低优先级优先，以及 `weighted_random` 和 `weighted_round_robin` 的单次、按权重选择。
- [x] 3.3 实现渠道运行状态（in-flight、连续连接失败、冷却、被动成功恢复），并使其独立于快照替换。
- [x] 3.4 将选路租约接入代理生命周期：仅响应头前的连接类失败影响健康状态；响应头或首字节后绝不重试或切换渠道。
- [x] 3.5 添加候选编译、优先级、权重分布、熔断冷却、取消释放和无重试的单元与隔离集成测试。
- [x] 3.6 运行格式化、静态检查和全部测试，并提交阶段 3。

- [x] 将单渠道模型规则扩展为已编译的渠道组选项和直接渠道候选项。
- [x] 实现最低优先级优先、同优先级按权重的单次选择。
- [x] 在快照外维护渠道运行状态：in-flight、连续失败、冷却和被动恢复。
- [x] 仅在响应头前记录连接类失败；响应头或任一响应字节后绝不重试或切换渠道。
- [x] 添加权重分布、优先级、熔断、冷却、取消和无重试测试。

## 阶段 4：控制面管理能力

阶段目标：通过独立的本地管理监听器安全地修改控制面；每次成功写入必须在一个事务中验证完整快照、写入脱敏审计记录并在提交后立即发布。

### 阶段 4 执行任务

- [x] 4.1 增加 TOML 管理监听器和启动时哈希的 bootstrap Bearer 管理员凭据；管理端默认禁用，启用时必须环回绑定、配置活动 actor 用户和高熵令牌。
- [x] 4.2 提取由定时重载和管理写入共用的发布协调器，使用同一进程内串行门和 `SERIALIZABLE` 数据库事务。
- [x] 4.3 实现 API Key、渠道组、渠道和模型规则的列表、读取、创建与全量更新/状态变更管理接口；普通响应一律脱敏且不物理删除记录。
- [x] 4.4 对每项管理写入，在提交前通过该事务读取并编译完整候选快照；将 allowlist 脱敏的 before/after 和关联 ID 写入同事务 `audit_logs`。
- [x] 4.5 仅在数据库提交成功后调和选路状态并发布 ArcSwap 快照；失败、校验拒绝或并发版本冲突不得改变数据库、审计记录或当前快照。
- [x] 4.6 添加管理认证、事务回滚、脱敏审计、立即快照发布及公共监听器不暴露管理路由的隔离集成测试。
- [x] 4.7 运行格式化、静态检查和全部测试，并提交阶段 4。

## 阶段 5：准入控制

阶段目标：在每个代理请求进入解析和选路前实施进程内 RPM、并发和软额度准入；运行状态独立于 ArcSwap 快照，并在任意终态释放并发租约。

### 阶段 5 执行任务

- [x] 5.1 将 API Key 的 RPM、最大并发、额度上限和已结算用量编译为不可变策略；`tokens_per_minute` 继续明确拒绝，因当前请求/响应路径不解析 token 用量。
- [x] 5.2 实现按稳定 API Key ID 索引的进程内 `AdmissionRuntime`：固定一分钟窗口 RPM、in-flight 计数和不可克隆租约；状态不随快照替换重建。
- [x] 5.3 在认证和代理权限校验后、读取 body 前执行准入：达到 RPM/并发限制返回 OpenAI 兼容 429；额度采用软已结算用量预检查（`used >= limit` 拒绝），不预留或结算金额。
- [x] 5.4 将租约覆盖 body 读取、选路、上游请求和响应流；成功、上游失败、格式错误、无路由和客户端取消均释放并发，RPM 不退款。
- [x] 5.5 在管理 API Key 创建和更新接口暴露 Stage 5 策略字段；配额已用金额仍由结算系统拥有且只读。
- [x] 5.6 添加 RPM 边界、并发/取消、软额度、跨格式共享、上游零接触、重载保留状态与策略变更的单元和集成测试。
- [x] 5.7 运行格式化、静态检查和全部测试，并提交阶段 5。

> 额度说明：此阶段只根据快照中的已结算 `quota_used_amount` 做软上限检查。当前不解析用量、没有价格快照或持久化结算，因此不计算、预留或释放货币金额；这些能力仍属于后续计费阶段。
